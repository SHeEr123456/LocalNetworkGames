## 1. 项目信息

| 项 | 内容 |
|---|---|
| 项目名称 | `local_network_games`（沿用现有包名 local-network-games） |
| 项目位置 | `E:\Projects\shenhechao\tank\LocalNetworkGames` |
| 编程语言 / 技术栈 | Node.js + `ws`（服务端）；**原生 JavaScript 无构建步骤**（客户端，WebSocket + Canvas/DOM） |
| 现有架构 | **服务端权威（Server-Authoritative）**：客户端只采集输入与渲染，全部规则判定在服务端 |
| 现状规模 | 13 个源文件、约 4300 行；含中国象棋 / 坦克大战 / 飞行棋 3 款 |
| 原始需求复述 | 让**大部分游戏**都能在这个平台上**免费、方便**地局域网游玩；优先覆盖①回合制桌游 与 ②实时对战街机 两大类；本次**仅规划**；技术路线**保持零构建原生 JS**（双击即用、手机开网页即玩）。 |

**现状关键事实（已读码核实）**

- 启动方式：`npm start` 或双击 `start.bat`，默认 3000 端口；其他设备访问 `http://<房主内网IP>:3000`。
- 通信协议已含 9 类客户端上行消息（`create_room`/`join_room`/`get_rooms`/`move`/`tank_input`/`flying_action`/`chat`/`restart`/`surrender`）。
- 服务端把「游戏差异」硬编码在核心文件里：`server.js` 的 `handleMessage` switch、`initializeGameState` switch、tick/广播/加入/离开/清理逻辑均按 `gameType` 分支。
- 客户端把「游戏差异」硬编码在：`OnlineGameApp.js`（静态 import 三款客户端 + `enterGame()` / `handleServerMessage()` 双 switch）、`index.html`（每个游戏一套独立容器）、`main.js`（手写 DOM 引用表）、`main.css`（每款游戏独立样式）。
- 结论：**新增一款游戏需同时改动 4~6 个核心文件，耦合度高、无统一抽象** —— 这是本次平台化改造要解决的核心矛盾。
- 已核实缺口：无账号与持久化（房间仅内存）、象棋无长将/和棋判定、飞行棋「跳/飞」未校验路径阻挡、断线后被直接踢回大厅（无重连）、无移动端专门适配（`main.css` 仅 `max-width:1024px / 600px` 两处断点，实时游戏无触屏操作层）。

## 2. 一句话产品定位

> **一个「零安装、零构建、无账号」的局域网游戏平台 —— 房主一条命令开局，同网设备打开网页即可玩，新增游戏只需丢一个目录。**

---

## 3. 产品目标（可度量）

把用户诉求「免费、方便」拆解为可量化指标：

| 编号 | 目标 | 度量指标（验收口径） |
|---|---|---|
| G1 | 零安装零构建 | `git clone` 后仅 `npm install && npm start`（依赖只有 `ws`）；仓库内**无打包/编译产物**、无构建脚本 |
| G2 | 房主一条命令启动 | 双击 `start.bat` 或 `npm start` 即完成，终端打印本机与内网访问地址（建议附二维码） |
| G3 | 新设备 10 秒进入对局 | 打开网页 → 连接 → 加入房间 ≤ 10 秒、≤ 3 步操作 |
| G4 | **新增游戏改动面最小化** | 目标：新增一款游戏**只新增一个游戏目录**，核心文件（`server.js` / `OnlineGameApp.js` / `index.html` / `main.css` / `main.js`）**零改动**（最多 1 处注册） |
| G5 | 手机可玩 | 竖屏 375px 宽可完整操作；触屏操作覆盖 100% 玩法动作 |
| G6 | 无外网依赖 | 运行时对外部域名（CDN/字体/图片）请求数 = 0，完全离线可用 |
| G7 | 无账号门槛 | 打开页面即可加入，注册/登录步骤 = 0 |
| G8 | 扩展节奏可控 | S 级游戏 ≤ 1 人日、M 级 ≤ 3 人日可上线（含联调） |

## 4. 目标用户与使用场景

### 4.1 目标用户

| 用户 | 特征 | 关注点 |
|---|---|---|
| 房主 / 组织者 | 一台电脑，愿意跑一条命令 | 开局快、不用配置、能随时换游戏 |
| 玩家（手机党） | 只带手机，扫码/输网址进房 | 免下载、点两下就玩、触屏顺手 |
| 玩家（电脑党） | 有键盘，偏好键鼠 | 操作跟手、画面不卡 |
| 扩展者（自己/朋友） | 想加新游戏 | 改动少、有模板可抄 |

### 4.2 典型场景

| 场景 | 描述 |
|---|---|
| 家庭聚会 | 客厅电脑当房主，家人用手机加入，玩五子棋/飞行棋等轻量回合制 |
| 宿舍 / 办公室午休 | 3~4 人、手机+电脑混合，短局快节奏，实时类为主 |
| 无公网环境 | 出差/内网隔离场景，无外网无服务器，纯局域网自建 |
| 临时加人 | 玩到一半来新人，能立刻开出新房间而不打断局中玩家 |
| 中途离场 | 有人走开断线，其余人可继续，不卡死整局 |

## 6. 需求池（P0 / P1 / P2）

优先级定义：**P0 = Must have（本迭代必须）｜P1 = Should have（重要、可延后）｜P2 = Nice to have（可选）**
分组说明：**A 组 = 平台化改造**（一劳永逸的底层能力）；**B 组 = 新增游戏**（内容增长）。

### A. 平台化改造需求

| 编号 | 需求 | 说明 | 优先级 |
|---|---|---|---|
| A1 | **统一游戏模块契约（服务端）** | 每个游戏导出标准接口：`createState(options)`、`onMessage(room, clientId, data)`（消息路由表）、可选 `tick(room, now)`（实时类）、可选 `serializeState(room)`（广播帧）、可选 `onPlayerJoin/onPlayerLeave/cleanup`。 | P0 |
| A2 | **服务端去硬编码** | `server.js` 只做 HTTP/WS/房间/大厅通用逻辑，按 `gameType` 查注册表分发；移除 `handleMessage`、`initializeGameState`、tick/join/leave 里的 `gameType` 分支。 | P0 |
| A3 | **统一游戏客户端契约** | 每个游戏导出标准接口：`manifest`（id/名称/人数/模式/操作方式）、`mount(ctx)`、`onState(state)`/`onEvent(event)`、可选 `onInput`、`destroy()`。 | P0 |
| A4 | **前端去硬编码 + 动态加载** | `index.html` 只保留一个通用游戏容器；`OnlineGameApp` 按 `gameType` 动态 `import()` 客户端模块；移除 `main.js` 手写引用表与双 switch。 | P0 |
| A5 | **游戏目录（Catalog）+ 游戏大厅** | 大厅从 `catalog` 动态渲染游戏卡片（图标/名称/类型/人数/模式）；房间列表按游戏过滤；创建房间可选游戏与人数。 | P0 |
| A6 | **移动端 / 触屏基础设施** | 响应式房间页布局（竖屏/横屏）+ 通用虚拟控制层（摇杆/方向键/手势）+ 触屏事件统一（禁用双击缩放与误滚动）。 | P0 |
| A7 | **房间生命周期完善** | 房间页「返回大厅 / 换游戏」；离房清理复用现有 `cleanupPlayerState` 思路并契约化；房间不再因单人练习而误判胜负。 | P0 |
| A8 | **断线重连（grace period）** | 客户端 `clientId` 持久化到 `localStorage`；服务端在玩家断开后保留席位一段时间（如 30s），重连即恢复该席位与权威状态。 | P1 |
| A9 | **进房二维码 / 分享链接** | 房主端展示「内网地址 + 房间号」二维码与可直接入房的链接，减少手输。 | P1 |
| A10 | **对局计时 / 回合倒计时** | 回合制加走子计时，实时类加对局时长；超时可选自动判负/跳过。 | P1 |
| A11 | **昵称（轻量、无账号）** | 进房前填一个昵称，用于玩家列表与聊天展示；仅存内存+本地。 | P1 |
| A12 | **观战模式** | 满员房间可旁观，只读接收权威状态。 | P2 |
| A13 | **单机 / AI 练习模式** | 无需第二人即可练习（客户端内置 AI 或服务端托管 AI 席位）。 | P2 |
| A14 | **本地战绩 / 对局统计** | 浏览器本地记录胜负局数，不做服务端持久化。 | P2 |

## 7. 游戏清单与优先级

**复用模式对照**

- **象棋式回合制**：服务端校验单步 → 广播该步（现有 `move` 流程）。
- **坦克式 tick 实时**：服务端固定 tick 循环 → 广播权威状态帧（现有 20FPS `tank_state` 流程）。

难度：**S** = 简单（规则少/无 AI）、**M** = 中等（需状态机或翻转/位运算）、**L** = 复杂（完整竞赛规则）。
触屏友好度：**5** 最优 → **1** 最差。批次：第一批（随平台化一起交付）/ 第二批 / 第三批。

## 8. UI / 交互方向

### 8.1 页面结构（三段式）

```
① 游戏大厅 (Lobby)
   ├─ 连接区：服务器地址（局域网访问时自动填充当前 host）
   ├─ 游戏目录：卡片网格（图标 + 名称 + 类型[回合/实时] + 人数 + 操作方式）
   └─ 房间列表：按游戏可过滤；卡片显示 房间号 / 游戏 / 人数 x/max / 状态(等待中/对局中) / 创建时间
② 统一房间页 (Room)
   ├─ 顶部栏：返回大厅 · 游戏名 · 房间号(可复制) · 分享/二维码
   ├─ 主区：游戏画布/棋盘（响应式，占据主视觉，等比缩放）
   ├─ 侧栏/底栏：玩家列表(颜色/状态) · 回合或计时 · 操作区(掷骰/认输/重开/音效) · 聊天
   └─ 触屏控制层（仅实时游戏渲染）
③ 通用覆盖层：结果弹窗、骰子/提示动画、Toast
```

> 关键改造：`index.html` 的「每个游戏一套容器」收敛为**单一 `<div id="game-stage">`**，由游戏模块自行挂载；公共 Header/玩家列表/聊天/操作区由平台统一提供。

### 8.2 响应式适配

| 方向 | 布局 |
|---|---|
| 桌面（≥1024px） | 主区居中，右侧信息栏（玩家/聊天/操作）常驻 |
| 平板 / 手机横屏 | 左主区 + 右信息栏；实时游戏触控层叠于主区左右下角 |
| 手机竖屏（≤600px） | 主区置顶满宽；信息区收为底部抽屉/Tab（玩家 / 聊天 / 操作）；**实时游戏建议横屏提示**（提供「请横屏以获得更好体验」引导，非强制） |

### 8.3 触屏操作方案

| 游戏类型 | 操作 | 方案 |
|---|---|---|
| 回合制桌游 | 点选棋子 → 点目标格 | 复用象棋点选/点走（`valid-move` 高亮）；触控热区放大到 ≥ 44px；禁双击缩放 |
| 实时·移动射击（坦克/飞机） | 移动 + 射击 | **左虚拟摇杆（8 向）** + **右射击按钮**；支持多点同时按下 |
| 实时·简单移动（贪吃蛇/相扑） | 方向 | 左**四方向虚拟键** 或 **滑动手势**；二选一或可切换 |
| 实时·挡板类（Pong/打砖块） | 拖动 | 主区内**横向拖动 / 触摸跟随** |
| 通用 | 缩放/滚动 | `touch-action: none` 于游戏区；`viewport` 自带 `user-scalable=no`；用 Pointer Events 统一鼠标/触摸 |

## 9. 非目标（本期明确不做）

- 不做账号体系、服务端持久化、跨公网联机（仍以局域网内即玩为边界）。
- 不引入任何构建工具 / 框架 / `npm` 前端依赖（保持零构建原生 JS）。
- 不做匹配排位、反作弊、付费等运营能力。
- 本期**不写实现代码**，仅输出规划与契约约定。
